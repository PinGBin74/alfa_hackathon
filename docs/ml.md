# ML-часть: как сервис превращает новость в персональный инсайт

Все LLM-вызовы - только к моделям из Приложения 3 через прокси организаторов. Агентная логика,
поиск, ранжирование и проверки написаны командой, без агентных фреймворков.

```
CSV клиентов/платежей ─► профиль + группа + граф контрагентов ─► чувствительность к факторам (правила)
                                                                        │
RSS/URL ─► извлечение ─► дедуп ─► разметка (Gemma) ─► news ─────────────┼─► ранжирование ─► лента
                                                                        │
PDF банка ─► текст (слой PDF / OCR) ─► фрагменты + позиции банка ───────┴─► агент: план ─► инструменты
                                                                              ─► черновик (GLM) ─► проверка (правила + DeepSeek)
                                                                              ─► адаптация ─► очистка ─► инсайт + трасса
```

## 1. Бизнес-контекст клиента (`services/client_profile.py`, `services/counterparty_graph.py`)
- **Профиль**: отрасль (ОКВЭД), масштаб (выручка, порог крупного бизнеса 15 млрд), штат, регион, продукты в банке,
  ВЭД и страны (ФТС, список через запятую разбивается), статус `CLIENT/PROSPECT/CLOSE_CLIENT`.
- **Группа компаний** (`GROUP_ID`): размер, суммарная выручка, отрасли участников по выручке.
- **Положение в отрасли**: место по выручке и доля выручки внутри класса ОКВЭД в выборке банка (это не доля рынка).
- **Граф платежей**: `PAYER` - отправитель, `BENEFICIARY` - получатель, значит поставщики - кому платит клиент,
  покупатели - кто платит ему. Платежи внутри своей группы считаются отдельно (у части клиентов это 90% закупок),
  оборот с контрагентами вне выборки - тоже (обычно 60-90%: их отрасль неизвестна). Для внешних контрагентов -
  топ, отрасли с долями и примерами, концентрация HHI.
- **Очистка при загрузке** (`db/seed.py`): разделитель `;`; id `U_428697` стоит у 12 разных компаний - удалён отовсюду;
  связи физлиц с компаниями вне выборки (63%) и платежи самому себе (27 тыс.) отброшены, повторы пар суммируются.

## 2. Таксономия факторов (`ml/taxonomy.py`)
18 факторов (ставка, инфляция, курс, долговой рынок, нефть, металлы, золото, агро, потребление, труд, рост ВВП,
налоги, регулирование, санкции/пошлины, логистика, недвижимость, энергетика, события компаний) - общий словарь
для разметки новостей, позиций банка и чувствительности клиента.

`exposures(profile)` - детерминированные правила «признак клиента → чувствительность к фактору» с объяснением.
Примеры: кредит/лизинг/депозит → ставка; ФТС и страны → курс и пошлины; своя отрасль, отрасли группы и
контрагентов по платежам → сырьевые и отраслевые факторы; штат и зарплатный проект → рынок труда.
Для торговли (45-47) учитывается, **продукцией какой отрасли** торгует компания (46.72 → металлургия, 46.21 → зерно).
Роль пользователя меняет приоритеты (`ROLE_WEIGHTS`: казначею важнее ставка, курс и облигации, главбуху - налоги).
`product_hints` - кандидаты для нативного предложения продукта банка (факторинг при концентрации покупателей и
отсутствии факторинга, хеджирование при ВЭД и т.п.); модель упоминает продукт, только если он следует из вывода.

## 3. Ранжирование (`services/ranking.py`)
`score = 0.40·factor + 0.25·industry + 0.10·geo + 0.15·importance + 0.10·freshness`; лента (`GET /api/feed/{client_id}`)
считает его для роли вошедшего пользователя, как и инсайт.
- factor - чувствительность клиента к факторам новости × вес роли; главный фактор новости весит больше.
  Меры, бьющие по конкретным товарам/странам (пошлины, регулирование), без совпадения страны или отрасли
  учитываются частично.
- industry - новость про отрасль клиента / его товара / группы / контрагентов (широкий класс «опт вообще» - слабый сигнал).
- geo - регион клиента или страны его ВЭД в новости.
Каждая компонента возвращает причину с кодом признака - её видит пользователь («почему это в ленте») и агент.

Поправки против ложных совпадений (найдены на eval-наборе real, подтверждены на отложенном holdout, раздел 6):
- новость, где перечислено больше 2 отраслей, - совпадение отрасли × 2/N («инвестиции в ТОР по 6 отраслям» -
  не новость про металлургию);
- главный фактор новости макроэкономический (ставка, инфляция, курс, ВВП, налоги...) - отраслевое совпадение ×0,4:
  решение ЦБ размечено отраслью 64, но это не новость банковской отрасли для клиента;
- страна ВЭД клиента в списке больше 3 стран - ×3/N (рейсы «в Баку, Тбилиси, Дубай...» - упоминание, а не событие);
- итог × (0,5 + 0,5 × важность): мелкое событие (важность 1-2), совпавшее с признаками, не обгоняет решение,
  которое меняет условия для всех заёмщиков.

**Поиск без эмбеддингов.** В списке моделей кейса (Приложение 3) эмбеддинг-модели нет: ключ команды открывает только
шесть LLM (`GET /v1/models`), `/v1/embeddings` прокси отклоняет с 403 (проверено 23.10). Поэтому поиск по аналитике
банка и новостям (`rag/retriever.py`) - лексический BM25 с русской нормализацией (стоп-слова, ё/е, лёгкий стемминг:
«ключевой ставки» находит «ключевая ставка») и бустом позиций банка по факторам таксономии, свежести и актуальности
прогноза. Смысловую близость, которую дали бы эмбеддинги, заменяет общий словарь факторов: новость, позиции банка и
чувствительность клиента размечены одними кодами. Компонента `semantic` в формуле ранжирования есть, но с весом 0;
колонки `embedding` и HNSW-индексы в БД оставлены на случай, если организаторы разрешат модель (`rag/embeddings.py`).

## 4. Агент (`agent/`)
| Требование кейса | Реализация |
|---|---|
| Планирование | `planner.py`: Gemma выбирает фокус-факторы, гипотезы и шаги (граф, поиск позиции банка по каждому фактору, связанные новости); валидатор добавляет обязательные шаги. Gemma изредка зацикливается и пишет 8192 токена за 2 минуты, игнорируя max_tokens (2 из 35 вызовов), поэтому у неё таймаут 25 с без повтора, затем план строит GLM (5-6 с), и только потом - детерминированный план |
| Инструменты | `tools/registry.py` под allowlist: профиль, граф, новость, поиск новостей, поиск аналитики банка; все только читают данные |
| Контекст | `state.py` хранит результаты шагов; `context.py` собирает один контекст: признаки с кодами, чувствительность, причины ранга, новость, позиции банка, продукты-кандидаты, списки допустимых source_id и признаков |
| Самопроверка и адаптация | `verifier.py`: правила (ссылки только на найденные источники; числа в фактах и позиции банка есть в цитируемом тексте; прогноз из материала, который банк позже обновил, - замечание `stale_bank_view`; каждый пункт «почему важно» опирается на признаки; рыночная позиция банка по фактору события не пропущена - позиции о конкретных эмитентах, `company_event`/`regulation`, не обязательны) + фактчекер DeepSeek (пересказ, атрибуция банку, противоречия, устаревшие прогнозы). При замечаниях `orchestrator._adapt` ищет дополнительные материалы банка/новости и пересобирает черновик с замечаниями (не больше 2 итераций: черновик и точечная правка) |

Черновик пишет GLM-5.3-Flash, проверяет другая модель - DeepSeek (своя модель плохо ловит свои ошибки).
Вторая итерация - точечная правка: модель получает свой черновик и замечания и меняет только отмеченные пункты
(полная пересборка каждый раз вносила новые ошибки, и проверка не сходилась). Что не исправлено за 2 итерации -
удаляется (`_drop_flagged`), удаление видно в `verification.issues` и трассе. Затем `_sanitize`: факт без
подтверждения и позиция банка без цитаты удаляются, прогноз банка, ошибочно записанный в «факты», переносится в
`bank_position`, коды признаков в `basis` заменяются ссылкой на данные клиента, продукт не из кандидатов становится
обычным действием. `confidence`: `high` - прошло сразу, `medium` - после правки/удаления, `low` - проверка не пройдена.

Актуальность аналитики банка: позиции с прогнозом связаны с более свежей версией (`superseded_by`); фрагмент PDF
со страницы, где есть обновлённый позже прогноз, помечается так же и ранжируется ниже; «срок прогноза наступил»
считается на сегодня. Модель видит в контексте пометки «ОБНОВЛЁН: актуальная версия - «название», дата [ссылка]» и
«срок прогноза уже наступил»; промпт черновика требует брать актуальную версию, а свои выводы класть не в
`bank_position`, а в `ai_inference` (с примером «плохо/хорошо»).

Замер на живых моделях (клиент U_9250, новость о ставке, роль CFO): 1-1,5 мин и ~0,7-1 ₽ на инсайт
(план 6 с, черновик 15-20 с, фактчекинг 8-10 с). Фактчекер ловит реальные ошибки: тезис главы ЦБ, поданный как
позиция банка; обратное направление связи «ставка - курс»; цифру из другого документа.

Результат - `contracts/insight.schema.json`: `what_happened` (подтверждённые факты / допущения),
`why_it_matters` (с кодами признаков клиента), `consequences` (риски/возможности с источниками),
`suggested_actions`, `bank_position` (только из аналитики банка, со ссылкой `bank:<doc>:<page>`),
`ai_inference` (выводы модели), `sources`, `verification`, `trace_id`.
Трасса (`agent_traces`): план, каждый вызов инструмента и LLM (модель, токены, цена, время), контекст клиента
(чувствительность, причины ранга), замечания проверки, адаптация, очистка.

Чат (`agent/chat.py`, `POST /api/chat`): уточняющий вопрос к инсайту (с историей разговора - до 6 реплик) → профиль
и граф клиента, поиск по аналитике банка и новостям → ответ Qwen3.6 со ссылками, неизвестные источники
отбрасываются; числа ответа сверяются с переданными данными, при расхождении - одна точечная правка (в живом
прогоне модель придумала «падение спроса на 20%» - такие цифры теперь ловятся); шаги - в отдельной трассе.

Новость по ссылке (`ingestion/manual.py`, `POST /api/news`): любая публичная статья проходит тот же конвейер, что
и RSS (защита от SSRF, извлечение текста, дедупликация, разметка Gemma), и по ней сразу можно получить инсайт -
так проверяется работа на новостях, которых не было в базе.

## 6. Качество (`eval/run_eval.py`, отчёты - `eval/reports/`)
Три набора. **synthetic** - 16 заранее известных событий × 5 реальных клиентов из выгрузки: регрессия логики.
**real** - 80 реальных новостей из 8 RSS-лент 23.10.2026 (день заседания ЦБ), прогнанных через продовый конвейер
(`collect`); на нём искались ошибки и подбирались правки. **holdout** - отложенные 50 реальных новостей 14-23.10
(без пересечения с real, `collect --set holdout`): правки проверялись на нём один раз, после выбора варианта на real.
Эталон real и holdout размечен вслепую, без доступа к разметке Gemma и к ранжировщику (`eval/golden_*_{real,holdout}.jsonl`).
Тексты статей в git не хранятся, только заголовки, ссылки и разметка (`eval/fixtures/news_{real,holdout}.jsonl`).

**Разметка новостей** (`classify`):

| Набор | Фильтр «про бизнес» (точность) | Главный фактор = эталон | Главный в эталонном наборе | Факторы P/R | Отрасли P/R | Страны P/R |
|---|---|---|---|---|---|---|
| real (78) | 0,94 | 0,83 | 0,96 | 0,62/0,94 | 0,54/0,69 | 0,77/0,81 |
| holdout (49) | 1,0 | 0,68 | 0,89 | 0,63/0,86 | 0,64/0,73 | 0,91/0,84 |

Модель надёжно отсеивает неделовые новости и почти не теряет нужные факторы (recall), но добавляет лишние
(company_event, regulation, consumption; отрасль 64 у решений ЦБ). Поправки ранжирования ниже гасят именно этот шум.
Сбой разметки - 1 из 80 (битый JSON на длинной речи); новость не теряется, её повторит следующий запуск планировщика.

| synthetic (16) | 0,963 / 1,0 / 2 | 0,979 / 1,0 / 0 | 0,778 / 1,0 / 3 | - | 0,36 |
| real (73) | 0,608 / 0,67 / 6 | 0,827 / 0,93 / 2 | 1,0 / 1,0 / 0 | 0,011 | 0,39 |
| holdout (46) | 0,570 / 0,80 / 8 | **0,754 / 0,93 / 5** | 0,657 / 0,73 / 5 | 0,157 | 0,26 |

Вариант правок выбран на real до прогона holdout (прототип: `ranking` с перебором вариантов на synthetic и real).
На holdout персональная лента лучше и хронологической, и сортировки по важности; на real сортировка по важности
идеальна потому, что в день заседания ЦБ решение по ставке (10 материалов с важностью 5) релевантно всем
клиентам с кредитами, а nDCG не штрафует повторы одного события. Ленты разных клиентов различаются (Jaccard топ-5
0,26-0,39 против 1,0 у общей ленты).

Во всех инсайтах каждый пункт «почему важно» опирается на признаки клиента и у каждого вывода есть источник.
Правки агента: промпт черновика (позиция банка - только слова банка, выводы - в ai_inference), пометка обновлённых
прогнозов и наступивших сроков, детерминированная проверка `stale_bank_view`, `missing_bank_view` без позиций об
эмитентах; оценка судьи за позицию банка выросла на 0,7-1,0, за факты - на 0,2-1,0. Остающиеся претензии судьи:
сопоставление несопоставимых прогнозов (конец года против среднегодового), «банк ожидал паузу» без явной даты
материала, неявное продвижение продукта. Часть претензий - ошибки самого судьи (выдуманная дата «25 октября 2025»,
«нет данных о заседании 23 октября», хотя оно в тексте новости; «дефицита 5,8 трлн нет в источнике» - судье передаются первые 2500 символов страницы, а число стоит на 2593-м): оценки судьи - ориентир, а не эталон.
Время: в живом прогоне через интерфейс (новость «Минэкономразвития о дорогом кредите», роль казначея) - 73 с.

**Позиции банка** (`data/bank_analytics/positions.json`): 88 позиций из 9 документов, все 88 прошли детерминированную

## 7. Безопасность AI-компонента
- Текст новостей и документов передаётся модели только внутри `UNTRUSTED_SOURCE` и сканируется на инъекции.
- Инструменты агента - allowlist, только чтение; модель не может вызвать то, чего нет в списке.
- Ссылки на источники и признаки проверяются по спискам, числа - по исходному тексту; непроверенное удаляется.
- В промпты попадают только обезличенные признаки клиента; бюджет LLM ограничен на уровне клиента и прокси.

## 8. Масштабирование
Новый фактор или отрасль - запись в `taxonomy.py` (ключевые слова, сектора, правило); новый источник новостей -
класс в `ingestion/sources`; новый документ банка - PDF в `data/bank_analytics` (текст или OCR) и запуск извлечения
позиций; качество контролируется тем же `eval`.
